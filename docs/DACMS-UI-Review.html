Verdict: a broad, working prototype wearing product clothing. The domain coverage is real and the NWU palette is pleasant, but the interface behaves like 33 pages built by different people on different days. There is a design system in index.css that almost nothing follows, three status languages, 17 hand-built tables, and a dozen controls that lead to the same place. A user who knows Moodle, Workday, Jira or Stripe will not be lost because the domain is hard — they will be lost because the app breaks the conventions they rely on.

This document is ordered by leverage: what is inconsistent, what is duplicated, what the dashboards are actually worth, and how to restructure the system so that prior experience transfers.

Five findings that matter most

  1. The design system is advisory, not enforced. Every page re-decides typography, spacing, table styling and colour. Consistency is maintained by memory, and memory has failed.
  2. Status is not a shared language. The same claim is Pending in one place and grey in another, Verified on one screen and Approved on the next, and yellow on a third. One claim, four truths.
  3. Duplicate entry points hide the real flow. “Submit Claim”, “Generate New Claim” and “Generate Claim” all lead to a list, not to the wizard; two admin buttons lead to the same screen; two export buttons on one page do the same thing.
  4. Dashboards report, they do not direct. They answer “what exists” rather than “what needs me now”. Metrics have no period, denominator or delta; the work queue is either absent or below the fold.
  5. One review screen is unreachable. ApplicationReview.jsx (414 lines) is routed at /application-review/:id but nothing links to it; the live review lives inline in ReviewApplications.
How this was assessed. All 33 pages in frontend/src/pages were read, then exercised live against the Docker stack as a student (Naledi), lecturer (Alan) and administrator (Eric). Findings below cite files and line numbers where the cause is unambiguous. Contrast ratios were computed from the theme tokens in index.css.

2Design consistency

2.1 A design system exists on paper only

frontend/src/index.css defines primary, neutral, success, warning, error, light-grey, off-white, radii and font families. Page code then ignores it:

  • 348 uses of raw gray-* — 195 of them text-gray-* — against the theme’s neutral. CreateBudget.jsx hardcodes the palette six times: bg-[#F8F9FA], bg-[#6C3D91], hover:bg-[#5A3280].
  • Three page-header bars: bg-primary px-8 py-4 on 17 pages, bg-primary h-16 px-4 md:px-8 on 15, and bg-primary h-16 px-8 on 2. Only the middle one is responsive; the others keep fixed px-8 on phones.
  • 93 section headings across three sizes for one semantic level: 18× text-3xl, 44× text-2xl, 31× text-xl. “Overview” is 30px on the lecturer dashboard and 24px on the student dashboard.
  • The title is printed twice. The page bar says “Work Tracking”, then the page repeats “Work Tracking” as an H2. Same pattern on Claims, Applications, Verify Hours and Appointment Approvals.
  • Seventeen tables, one shared component. Only AuditLogs uses CompactTable; the other 16 pages build their own, with three header treatments, three row heights and three action styles.
  • Cards look unfinished. Card.jsx applies border border-dark — a near-black outline on every surface — which fights the soft purple shadow and makes the UI read as a wireframe.

There is no single source of truth for what a status means or how it looks:

  • The same claim is Verified on Claims Verification and Approved on Export Payments. The lifecycle verified → approved → paid must be distinct and labelled once.
  • “Under Review” rendered as red (bg-error) reads as failure rather than progress.

2.3 Numbers and dates are formatted ad hoc

Within a single session the same money appears five ways: R 45 052,96 (lecturer), R 563,88 (student dashboard), R 260.25 (work tracking), R 107,8 (export) and R 1 078 (dashboard). Dates appear as 07 Oct 2026, 07 October 2026 and raw 2026-10-07 in the work-session table. Consolidate into one formatMoney and one formatDate; ban toFixed in page code.

2.4 Feedback, loading and empty states

  • No toast, modal, dialog or drawer primitives exist anywhere. Feedback is per-page banners; StudentModules.jsx:169 falls back to window.confirm.
  • Summary cards render 0 while loading, so the admin dashboard shows “Pending Claims 0” and then 4. Use skeletons, or — as the student dashboard sometimes does.
  • Fifteen “Loading…” states are plain text in cards; fifteen empty states are plain text with no call to action.
  • Submission does not consistently disable the trigger; the export page instead lets you click and then tells you to select a claim.

2.6 Brand and vocabulary

  • The repository and README say DACMS; the navbar, login, landing page and 30 document titles say AACMS; StudentModules.jsx says DACMS. Pick one.
  • “Demi” and “Assistant” describe the same person (“Approved Demis”, “Total Assistants”, “Apply for Assistant”). A student outside NWU will not know “demi”.
  • One destination, three names: sidebar “Assign Duties”, page “Assign Assistant Responsibilities”, route /assign-responsibilities. Same for “Verify Hours” versus “Verify Work Hours”.
  • Singular/plural on one screen: H1 “Appointment Approvals”, H2 “Appointment Approval”.
  • Truncated values: in Student Profile, “Person Type” and “Justifiable Reason” both display “Student Assis…” inside 3-column inputs at 802px, so the user cannot read their own selection.

3.2 Interactions that appear to work but do not

  • VerifyWorkHours.handleApprove() (lines 180–200) shows “All work hours have been approved” without calling any API. Reject is a message telling the user to ask the backend team.
  • Admin claim rejection is a “not currently available” message (ClaimReview.jsx:228); forgot password throws “not available yet”.
  • Admin login returns HTTP 202, then AuthContext.login calls response.json() twice (lines 46–53), so the 2FA flow throws before it can complete.
  • ProtectedRoute is a no-op, and public registration offers “Administrator” as a self-service role — a security problem wearing a UI costume.

4Dashboard value

4.1 Student dashboard — 40% signal

Valuable: active positions, hours this month, pending claims, application statuses, monthly hours per module.

Noise: the “Generate Claim” card duplicates quick actions and the Claims page; “Recent Activity” duplicates notifications; a two-column table is used for two modules.

Missing: what needs attention now — unverified sessions that block a claim, a claim window closing, outstanding money, profile incompleteness.

Replace with: four KPIs with deltas (hours this month vs last, unverified sessions, claims awaiting action, earnings paid/pending), a “Needs your attention” queue, at most two quick actions, then the claims table. Move monthly hours to the Work page.

4.2 Lecturer dashboard — 55% signal

Valuable: applicants, pending applications, claims summary, sessions awaiting verification, budget utilisation.

Noise: “Approved Demis”; “Hours Allocated 480h” with no cap or denominator; the full budget module list, which belongs on Budgets.

Missing: one ordered approval queue (applications + hours + claims) with counts and age; cap warnings at 80/120 hours per assistant; projected budget overspend.

Replace with: action queue first, portfolio KPIs second, budget health third. Fix the all-yellow badges before anything else.

4.3 Admin dashboard — 30% signal

Valuable: pending claims (4), pending appointments, monthly claims spend.

Noise: “Total Modules / Lecturers / Assistants” (vanity, never changes); six months of rows including four R 0s; “Monthly Work Sessions” with two months and no CTA; “Administrator Actions” (the sidebar already does this); “Claims Export” card (duplicates a nav destination); and a fifth stat card orphaned in a three-column grid.

Missing: exceptions — budgets near limit, claims pending beyond N days, unverified sessions, payment batch status, spend versus allocated year-to-date, an “as of” timestamp.

Replace with: an attention strip (“4 claims to verify · 0 appointments · 2 budgets near limit”), a KPI row with period selector and deltas, one spend trend chart, top-five budget burn, and recent admin activity from the audit log. Delete the action buttons and export card; make them navigation and header actions.

Bug: AdminDashboard.jsx:38–55 uses ?? 'null', so a missing value literally renders the string null.

4.4 Rules for every dashboard

  1. Every metric needs a period and a denominator (spent of allocated, hours of cap).
  2. At most one chart per dashboard. A table of months with zeros is not a chart.
  3. Anything clickable must be the only path to that destination, not a third one.
  4. Put the work queue above analytics: people open dashboards to decide what to do next.

5.1 Conventions users already know

The app omits the furniture that makes Workday, Moodle, Jira and Stripe predictable:

  • User menu with name, role, settings and logout in the top-right. Today the bar has only a bell; logout sits at the bottom of the side nav; admin audit logs are a mystery icon.
  • Breadcrumbs on detail pages (Claims / CLM-2026-01011), not a “← Back to Dashboard” link on one page only.
  • Data tables with sort, pagination, bulk select, priority columns and a sticky action column. Today the Claims table hides Amount, Status and “View Details” off-screen; Export wraps Claim ID and Date onto three lines.
  • One detail pattern — drawer or route — with a status stepper. ApplicationDetail already has “Approval Progress”; generalise it.
  • Global search or command palette (Ctrl+K) for students, modules, claims and references.
  • Toasts and confirm dialogs instead of banners and window.confirm.
  • Settings in the user menu, not a “Comfortable view” button in the Audit Logs page header.
  • Empty states with a CTA (“No applications yet → Apply for an assistant position”).

Sequencing. Sprint 0 ships in week one even if everything else slips: it removes the lies and the dead ends that make every other improvement look cosmetic. The two-week sprints assume one frontend developer plus part-time design review; treat the ranges as indicative, double them for a solo effort, and split Sprint 1 across two developers only along the table/header seam.

P0 Sprint 0 — Correctness and trust

Sprint 0 is a demolition sprint, not a design sprint. One rule governs every item: keep the implementation that is already wired to the API and delete the other one. Do not create a ui/ folder, do not rename components, do not touch the 348 gray-* classes, do not restyle Card, and do not rebuild a dashboard. The sprint is roughly 22 developer-hours and should read as a small diff of deletions and one-line fixes.

Step 1 · Make the guard real 4 h

Files: routes/ProtectedRoute.jsx, contexts/AuthContext.jsx, pages/Login.jsx.

  • Replace the demo body of ProtectedRoute — currently return <Outlet /> — with the check below. Eight lines, no helper module, no new dependency.
const HOME = {
  student: '/student-dashboard',
  lecturer: '/lecturer-dashboard',
  admin: '/admin-dashboard',
};

const ProtectedRoute = ({ requiredRoles = [] }) => {
  const { user, loading } = useAuth();
  if (loading) return null;
  if (!user) return <Navigate to="/login" replace />;
  if (requiredRoles.length && !requiredRoles.includes(user.role)) {
    return <Navigate to={HOME[user.role] ?? '/login'} replace />;
  }
  return <Outlet />;
};
  • AuthContext.login reads the response body twice: the 202 branch calls response.json() at line 47 and line 53 calls it again, which throws. Read once, branch, return.
const data = await response.json();

if (response.status === 202) {
  navigate('/2fa', {
    replace: true,
    state: { from: data.requiresSetup ? 'setup' : 'login', user: data.user },
  });
  return null;
}

Acceptance checklist

  • Logged out, every role route redirects to /login; cross-role access lands on the user’s own dashboard.
  • One status word and one tone per state across all four screens; no white on warning or success.
  • Apply, Submit Claim and Export each reach their action in one click.
  • Approve and Reject exist only where the API supports them; no “ask the backend team” message remains.
  • ApplicationReview, PageNavigation, claimsData, the unused assets and the commented decision card are gone, and every remaining route is reachable from the UI.
  • npm run build passes and the diff contains no new components.

BProposed component contracts

<AppLayout role="admin" title="Claims" actions={<Button>New claim</Button>}>
  <PageHeader breadcrumbs={[...]} />
  <Section title="Awaiting verification">
    <DataTable
      columns={columns} rows={claims}
      sortable paginated selectable
      empty={<EmptyState action="Create the first claim" />}
      loading={loading} />
  </Section>
</AppLayout>

// One status vocabulary, one tone map
<StatusBadge status="Verified" />   // label + tone from STATUS

// One money/date contract
formatMoney(563.88)  // "R 563,88"
formatDate(iso)      // "07 Oct 2026"

Migration order: tokens and typography → Button and Card → StatusBadge → DataTable → AppLayout and PageHeader → forms and feedback. Each step is independently shippable, and each reduces the diff of the next.

Bottom line. The app has the right pages and the right data; it lacks a spine. Adopt a shell, a status model, a table and a feedback system; delete the duplicate entry points and dead review pages; rebuild the dashboards around “what do I need to do now” instead of “what can we count”. That alone moves it from “student project that works” to “system an NWU administrator can trust”.
